# CSPortfolio 极限压测记录

- 测试日期：2026-09-28
- 测试目标：验证 GitHub 最新重构版本在当前单机资源上的健康检查、首页 SSR、查询和最大文件上传能力。
- 测试镜像：`jxtd-refactor:github-c848948`
- 测试方式：隔离压测实例；不重启、不写入生产容器和生产数据库。
- 原始记录：服务器临时目录 `/tmp/csp-extreme-20260928/RESULTS.md`。

## 结论先行

1. health/ready 和查询接口在 400/200 VU 下仍无错误，数据库和健康检查路径余量较好。
2. 学生首页 50 VU 达到 p95 783 ms 且 0% 错误；100 VU 开始出现 0.61% 网络超时；200 VU 出现 6.3% 网络超时和 10 秒 p95，已经明显退化。
3. 25 MiB 简历上传在 1、3、5、10、20 并发下共 39 次全部 HTTP 200，无 OOM、死锁或 `.part` 半文件；20 并发 p95 约 2.621 秒。
4. 最大容器 RSS 为 236.3 MiB / 512 MiB，没有观察到内存打满。
5. 当前 VPS 对外只应承诺招新窗口的几十级并发。100 VU 以上是容量摸底，不是容量保证；如要提高首页容量，应先做 SSR/静态缓存优化或升级机器。

## 后续优化顺序

1. 先测首页当前 HTML、初始 JavaScript、SSR 时间和静态资源命中率基线。
2. 检查学生首页是否意外加载管理端组件或管理端依赖。
3. 对内容哈希的 `/_nuxt/*` 资源确保 Caddy 长缓存，HTML 不盲目长缓存。
4. 在不改变 API 行为的前提下减少首页 SSR 查询和首屏 JavaScript。
5. 使用与本轮相同的 50/100/200 VU 场景重新压测，比较 p50/p95/p99、错误率、CPU、RSS 和磁盘 I/O。
6. 如果目标超过当前单机能力，再评估升级 VPS；不要仅靠增加实例数掩盖内存预算和 SQLite 写入约束。

## 限制

- 本记录是当前机器和当前镜像的基线，不是 SLA。
- 网络超时包含压测客户端与服务端之间的连接等待，不能单独解释为数据库慢；后续应同时采集 Caddy access log、应用 `request_id` 日志、CPU、RSS、磁盘 I/O 和 SQLite busy/lock。
- 测试在隔离实例执行，不能推导真实公网链路下的所有结果。
- 任何上传路径、Caddy 配置、首页依赖或 SQLite 参数变化后，都必须重新建立基线。
